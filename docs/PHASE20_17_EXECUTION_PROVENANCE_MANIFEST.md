### 1. Architectural Purpose

To prevent plan tampering, replay attacks, cross-environment leakage, and time-of-check to time-of-use (TOCTOU) exploits, every OpenTofu plan generated by `TrustedPlanWrapperV17` must be accompanied by an **RFC 8785 Canonical JSON Execution Provenance Manifest**.

The manifest forms an immutable cryptographic envelope that binds:
1. The exact binary plan artifact (`savedBinaryPlanSha256`).
2. The exact JSON representation used for policy evaluation (`planJsonSha256`).
3. The exact HCL source configuration digest (`hclSourceConfigDigest`).
4. The exact provider dependency lockfile (`lockfileDigest`).
5. The toolchain version and executable digest (`engineVersion`, `engineBinaryDigest`).
6. The source control commit (`gitCommitSha`).
7. The operational environment context (`targetEnvironment`, `workspace`).
8. The policy approval verdict (`policyEngineApprovalHash`, `policyStatus`).
9. Temporal boundaries (`timestampIso`, `expiresAtIso` with a strict 2-hour window).

---

### 2. Canonical JSON Normalization (RFC 8785 / JCS)

Standard JSON serialization is non-deterministic due to whitespace variations, floating-point representation, and arbitrary key ordering. If two systems serialize the same logical JSON object differently, cryptographic signatures will fail.

`TrustedPlanWrapperV17` implements strict RFC 8785 (JSON Canonicalization Scheme):
- **Lexicographical Key Sorting:** Object keys are sorted strictly by Unicode code point values at all nesting levels.
- **Whitespace Elimination:** No extraneous whitespace outside of string literals.
- **Strict Scalar Encoding:** Strings use standard escape sequences; numbers adhere to IEEE 754 decimal representation without trailing zeros or exponential syntax where integers suffice.

### 4. Non-Secret Digest Policy vs Plaintext Leakage

To preserve strict confidentiality:
1. **No Sensitive Values in Manifest:** Plaintext variables (such as database credentials, tokens, or encryption keys) are NEVER embedded in the manifest.
2. **Resource Secret References:** Secrets are documented exclusively by their Cloud Secret Manager resource identifier (`projects/.../secrets/...`).
3. **Digest-Only Plan Representation:** The manifest contains only cryptographic digests (`SHA-256`) of the binary plan and JSON representation. Even if the manifest is stored in a publicly visible CI/CD pipeline or audit log, zero sensitive configuration data is disclosed.

---

### 5. Asymmetric Cryptographic Notarization

The execution provenance manifest is digitally signed using an asymmetric ECDSA key pair:
- **Algorithm:** ECDSA over NIST P-256 (secp256r1) with SHA-256.
- **Signing Key:** Managed by the CI Plan Notary Service (`sa-ci-plan-notary`). In production, this key resides in Cloud KMS HSM (`projects/.../locations/global/keyRings/ci-notary/cryptoKeys/plan-attestation-key`).
- **Signature Encoding:** Hexadecimal DER-encoded ASN.1 signature.
- **Verification:** The apply gate imports the notary's public key (PEM-encoded SubjectPublicKeyInfo) and verifies the signature over the RFC 8785 canonical bytes of the manifest. Any single-byte alteration to the manifest, plan hash, or commit SHA invalidates the cryptographic signature immediately.
