## Transaction-Bound ECDSA Signing & Canonical Verification Engine

**Project:** Kelasagara Major Project  
**System:** Worker Marketplace & Multi-Factor Biometric Identity Platform

## 1. TRANSACTION SIGNATURE OVERVIEW

To prevent man-in-the-middle attacks, credential replay, and request parameter tampering, every sensitive biometric operation (`/enroll`, `/verify-1to1`, `/replace`) requires a digital signature generated by the worker's device-bound private key.

The signature covers a deterministic canonical representation of the transaction, binding:
- The caller's Firebase UID.
- The registered `deviceKeyId`.
- The server-issued transaction challenge ID and nonce.
- The HTTP method and canonical route.
- An idempotency key.
- The cryptographic digest of the raw capture image payload (`SHA256(rawImageBytes)`).

---

## 2. LENGTH-PREFIXED CANONICAL BINARY SERIALIZATION

To guarantee complete bit-for-bit equivalence between TypeScript (backend) and Dart (mobile client), the transaction parameters are serialized into a binary buffer using 4-byte big-endian length prefixing for every field:

```
[Field 0 Length: 4 bytes BE][Field 0 UTF-8 Bytes]
[Field 1 Length: 4 bytes BE][Field 1 UTF-8 Bytes]
...
[Field 11 Length: 4 bytes BE][Field 11 UTF-8 Bytes]
```

### The 12 Canonical Fields of `PLAY_INTEGRITY_BINDING_V2`:
1. `protocolVersion` (`'PLAY_INTEGRITY_BINDING_V2'`)
2. `packageName` (`'com.kelasagaara.kelasagaara'`)
3. `appVersion` (`'1.0.0'`)
4. `authenticatedUid` (e.g. `'usr_worker_481516'`)
5. `deviceKeyId` (e.g. `'devkey_7a8b9c0d1e2f_99f8e7d6'`)
6. `challengeId` (e.g. `'tx_chal_a1b2c3d4e5f6'`)
7. `challengePurpose` (`'BIOMETRIC_ENROLLMENT'` | `'BIOMETRIC_VERIFICATION_1TO1'` | `'BIOMETRIC_REPLACEMENT'`)
8. `challengeNonceHash` (`SHA256(challengeNonce).hex`)
9. `httpMethod` (`'POST'`)
10. `route` (e.g. `'/api/biometrics/v10/enroll'`)
11. `idempotencyKey` (e.g. `'idem_tx_889900'`)
12. `payloadDigestSha256` (`SHA256(rawImageBytes).hex`)

### Why Length-Prefixing Prevents Delimiter Collisions:
In standard delimited strings (such as `field1 + "|" + field2`), an attacker can shift boundaries between fields if a delimiter is escaped or missing (e.g. `"abc" + "|" + "def"` vs `"ab" + "|" + "c|def"`). With 4-byte big-endian length-prefixing, each field boundary is strictly delineated by its byte length, rendering boundary-shifting mathematically impossible.

## 3. SIGNATURE GENERATION & VERIFICATION

### Client-Side (Kotlin via Android Keystore):
```kotlin
val privateKey = keyStore.getKey(alias, null) as PrivateKey
val signature = Signature.getInstance("SHA256withECDSA")
signature.initSign(privateKey)
signature.update(canonicalBytes)
val derSignatureBytes = signature.sign()
val signatureBase64 = Base64.encodeToString(derSignatureBytes, Base64.NO_WRAP)
```

### Server-Side (TypeScript via `node:crypto`):
```typescript
const canonicalBytes = serializeCanonicalBinding(bindingParams);
const sigBuffer = Buffer.from(signatureBase64, 'base64');
const verified = crypto.verify('sha256', canonicalBytes, publicKeyPem, sigBuffer);
```

If any single byte of the canonical input, camera image, challenge, route, or UID is modified in transit, `crypto.verify` returns `false`, and the request is immediately rejected with HTTP 403 (`DEVICE_SIGNATURE_INVALID`).
