## 1. Problem Statement: Mathematical Version Incompatibility

A core principle of biometric information theory is that **embeddings generated by different model architectures, projection matrices, or preprocessing pipelines are mathematically incompatible**, even if they share the identical vector dimensionality ($D = 128$).

```
+====================================================================================================+
|                                    MATHEMATICAL VERSION INCOMPATIBILITY                            |
+====================================================================================================+
|  1. Legacy v1 (Raw Landmarks):                                                                     |
|     - Space: Un-normalized positive orthant ℝ₊¹²⁸                                                  |
|     - Property: Highly sensitive to distance from camera and absolute bounding box size.          |
+----------------------------------------------------------------------------------------------------+
|  2. Legacy v2 (Harmonic Projection):                                                               |
|     - Space: S¹²⁷ with +0.28 constant DC cosine carrier offset: e = cos(πz) + 0.28                 |
|     - Defect: Severe collinearity; all human faces pointed into identical positive octant.        |
|     - Impact: Rama matched Kiran with ~91% similarity (False Duplicate Collision).                |
+----------------------------------------------------------------------------------------------------+
|  3. Production v3 (Rahimi-Recht Random Fourier Features Whitened):                                 |
|     - Space: True Gaussian RBF kernel embedding on S¹²⁷ with bandwidth σ = 4.2                     |
|     - Property: Centered zero-mean spatial whitening; analytical norm ||e||₂ ≡ 1.0000000.          |
|     - Impact: Strangers yield Sim ≤ 0.35 (mean 0.05); same-person re-scans yield Sim ≥ 0.85.      |
+====================================================================================================+
```

### Critical Invariant: Strict Comparison Prohibition
$$\text{If } \mathbf{T}_A.\text{modelVersion} \neq \mathbf{T}_B.\text{modelVersion} \implies \text{Comparison STRICTLY PROHIBITED}$$
Comparing a v2 template against a v3 template is mathematically undefined and yields arbitrary, corrupted cosine scores. Cross-version matching is prevented by code-level assertion guards in both Flutter client and Cloud Run backend engines.

## 2. Model Version & Envelope Metadata Contract

Every document stored in `biometric_vault/{uid}` must declare its full provenance contract:

```typescript
interface BiometricProvenanceContract {
  modelVersion: "kelasagara_biomatch_v3_whitened";
  preprocessingVersion: "rff_whitened_sigma_4_2";
  embeddingDimension: 128;
  normalization: "L2_HYPERSPHERE";
  envelopeVersion: "v3_kms_gcm";
  aadContext: {
    tenantId: "kelasagara_production";
    uid: string;
    modelVersion: "kelasagara_biomatch_v3_whitened";
  };
  schemaVersion: 3;
}
```

Any record missing these metadata fields or presenting an unregistered `modelVersion` is rejected by the matcher with an explicit `INCOMPATIBLE_TEMPLATE_VERSION` error.

## 3. The 5-Phase Zero Blind-Spot Migration Strategy

A common failure mode during biometric system upgrades is the **"Migration Blind Spot"**: if legacy templates are simply dropped or ignored during 1:N deduplication, a malicious user could register a duplicate account during the migration window.

Kelasagara implements a **Zero Blind-Spot Migration Strategy**:

```
+----------------------------------------------------------------------------------------------------+
| PHASE 1: PRE-MIGRATION BACKUP & ISOLATION                                                          |
|  - Execute full point-in-time snapshot of Firestore collection `biometric_vault`                   |
|  - Export encrypted records to cold Cloud Storage bucket: `gs://kelasagara-backup-vault-v2/`       |
|  - Verify SHA-256 backup manifest checksum                                                         |
+----------------------------------------------------------------------------------------------------+
                                                  |
                                                  v
+----------------------------------------------------------------------------------------------------+
| PHASE 2: CANARY PILOT & BENCHMARK VALIDATION                                                       |
|  - Migrate 50 volunteer internal test accounts to v3                                               |
|  - Verify 1:1 login verification pass rate (Target: >= 98.5%)                                       |
|  - Verify 1:N duplicate detection across canary cohort                                              |
|  - Validate KMS envelope unwrap latency (Target: < 25 ms)                                          |
+----------------------------------------------------------------------------------------------------+
                                                  |
                                                  v
+----------------------------------------------------------------------------------------------------+
| PHASE 3: LIVE IN-PLACE CLIENT RE-ENROLLMENT                                                        |
|  - App detects user has legacy v1 or v2 template                                                   |
|  - Displays bilingual `RetroactiveEnrollmentBanner` on Home Dashboard:                             |
|    "ಮುಖ ಗುರುತು ನವೀಕರಿಸಿ — Update Face ID for High Security"                                        |
|  - User performs a 3-second live blink capture                                                     |
|  - Extracted v3 template is scanned against all active v3 templates in RAM index                   |
|  - Upon deduplication clearance, v3 record atomically overwrites legacy document                   |
+----------------------------------------------------------------------------------------------------+
                                                  |
                                                  v
+----------------------------------------------------------------------------------------------------+
| PHASE 4: BACKEND ENVELOPE BATCH UPGRADE (State Machine MIG-01 to MIG-05)                           |
|  - Cloud Run batch worker inspects stored ciphertexts                                              |
|  - Converts legacy `v2_kms_legacy` envelopes to canonical length-prefixed `v3_kms_gcm` envelopes    |
|  - Migration is idempotent: already-migrated v3 records are safely skipped                         |
|  - Corrupted ciphertexts fail safely without damaging existing vault state                         |
+----------------------------------------------------------------------------------------------------+
                                                  |
                                                  v
+----------------------------------------------------------------------------------------------------+
| PHASE 5: SUNSET & LEGACY DECOMMISSIONING                                                           |
|  - 60-day grace period concludes                                                                   |
|  - Minimum envelope version set to `v3_kms_gcm`                                                    |
|  - Un-migrated legacy accounts prompted for mandatory re-scan upon next login                      |
+----------------------------------------------------------------------------------------------------+
```

## 5. Backend Migration State Machine (Tests MIG-01 to MIG-05)

The server-side migration worker (`backend/src/services/template_migration.ts`) enforces five formal invariant states verified by automated tests:

1. **MIG-01 (Dry-Run Preview):** Previews the migration batch and calculates expected transformation metrics without writing changes to Firestore.
2. **MIG-02 (Live Commit & Vector Fidelity):** Commits valid `v3_kms_gcm` records. Verifies that the decrypted embedding vector is bit-for-bit identical to the source vector.
3. **MIG-03 (Idempotent Execution):** Executing migration against an already-upgraded v3 record is an idempotent no-op and logs `MIGRATION_SKIPPED_ALREADY_V3`.
4. **MIG-04 (Atomic Failure Safety):** If a source record has corrupted ciphertext or an invalid auth tag, the migration aborts for that specific user without altering the document, logging `MIGRATION_FAILED_CIPHERTEXT_CORRUPTED`.
5. **MIG-05 (Heterogeneous Batch Handling):** Safely processes mixed batches containing v2, v3, and unenrolled records without cross-contamination.

## 6. Disaster Recovery & Rollback Runbook

If an unforeseen anomaly is discovered during Phase 3 or Phase 4 (e.g., unexpected camera driver incompatibility on a specific OEM device):

```
+====================================================================================================+
|                                    EMERGENCY ROLLBACK RUNBOOK                                      |
+====================================================================================================+
|  TRIGGER CRITERIA:                                                                                 |
|  - Systemic False Non-Match Rate exceeds 3.0% over a 1-hour window.                                |
|  - Cloud KMS decryption error rate exceeds 0.1%.                                                   |
|  - Cloud Run 1:N deduplication latency exceeds 200 ms.                                             |
+----------------------------------------------------------------------------------------------------+
|  ROLLBACK EXECUTION STEPS:                                                                         |
|                                                                                                    |
|  Step 1: Set Server Feature Flag                                                                   |
|    - Update environment variable: `FORCE_FALLBACK_SMS_OTP=true`                                    |
|    - Workers unable to verify biometrically are seamlessly routed to SMS OTP authentication.       |
|                                                                                                    |
|  Step 2: Revert Backend Minimum Envelope Version                                                   |
|    - Set `MIN_ENVELOPE_VERSION=v2_kms_legacy` in Cloud Run service configuration.                  |
|    - Allows backward-compatible reading of legacy v2 envelopes.                                    |
|                                                                                                    |
|  Step 3: Restore Vault Snapshot (If Data Corrupted)                                                |
|    - Run restore script: `tools/restore_vault_snapshot.sh gs://kelasagara-backup-vault-v2/`         |
|    - Overwrites damaged documents from the pre-migration snapshot.                                 |
|                                                                                                    |
|  Step 4: Rebuild RAM Index                                                                         |
|    - Invoke `POST /api/biometrics/rebuild-index` with admin master key.                            |
|    - Repopulates `InMemoryBiometricIndex` from restored records.                                   |
|                                                                                                    |
|  Step 5: Incident Post-Mortem                                                                      |
|    - Log root cause analysis in `docs/security/INCIDENT_LOGS.md` within 24 hours.                  |
+====================================================================================================+
```
